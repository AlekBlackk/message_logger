# message_log

Юзербот на Telethon: кеширует входящие сообщения Telegram и присылает в Избранное
отчёты об удалении и редактировании, с оригинальными медиафайлами.

Личный аккаунт, для личного использования. Требует MTProto — у Bot API нет события удаления.

## Установка

Нужен Python 3.10+.

1. `pip install -r requirements.txt`
2. `cp .env.example .env` и заполните `API_ID` / `API_HASH` с https://my.telegram.org
3. `python main.py` — Telethon запросит номер телефона, код входа и, если включена
   двухфакторная аутентификация, пароль. Будет создан файл `<SESSION_NAME>.session`.

Несколько аккаунтов одним процессом — см. [Несколько аккаунтов](#несколько-аккаунтов).

## Несколько аккаунтов

Один процесс может вести сразу несколько Telegram-аккаунтов — у каждого свой
`.env` (свой `SESSION_NAME`, `DB_PATH`, список отслеживаемых чатов и т.д.):

```bash
ACCOUNTS_ENV=acc1.env,acc2.env python main.py
```

Каждый аккаунт независим: своя сессия, своя БД, свой `/watch`-список. Если один
аккаунт падает (обрыв сессии, ошибка авторизации), остальные продолжают работать —
падение логируется, но не останавливает процесс. Если упали вообще все аккаунты,
процесс завершается с ненулевым кодом выхода.

## Конфигурация

| Переменная | Значение |
| --- | --- |
| `API_ID`, `API_HASH` | Данные с my.telegram.org. Обязательны. |
| `SESSION_NAME` | Имя файла сессии. По умолчанию `logger`. |
| `WATCH_CHATS` | Одноразовый посев БД при первом запуске, если список пуст. Дальше не читается — используйте `/watch`. |
| `IGNORE_CHATS` | Чаты, которые нужно пропускать. `LOG_TARGET` добавляется автоматически. |
| `LOG_TARGET` | Куда слать отчёты. `me` = Избранное. |
| `LOG_OUTGOING` | Также логировать удаление собственных сообщений. |
| `LOG_EDITS` | Присылать отчёт при редактировании сообщения. |
| `LOG_JOINS` | Присылать отчёт при вступлении/выходе участника в отслеживаемом чате. |
| `DOWNLOAD_MEDIA`, `MAX_MEDIA_MB`, `MEDIA_DIR` | Настройки сохранения медиа. |
| `DB_PATH`, `RETENTION_DAYS` | Расположение кеша и срок хранения строк. |
| `BACKFILL_ON_START`, `BACKFILL_LIMIT` | Прогрев кеша при старте. Нужен непустой `WATCH_CHATS`. |
| `LOG_LEVEL`, `LOG_FILE` | Уровень логов и файл, куда их писать (с ротацией, 5 МБ × 3). Пустой `LOG_FILE` — только консоль. |
| `RECONCILE_INTERVAL_MIN`, `RECONCILE_WINDOW_HOURS` | Периодическая сверка кеша с Telegram, ловит удаления без апдейта. `0` в интервале выключает. |
| `PROXY_ENABLED`, `PROXY_TYPE`, `PROXY_HOST`, `PROXY_PORT` | SOCKS/HTTP прокси. |
| `ACCOUNTS_ENV` | Не в `.env`, а в окружении процесса: список `.env`-файлов через запятую, чтобы вести несколько аккаунтов одним процессом (`ACCOUNTS_ENV=acc1.env,acc2.env python main.py`). Не задано — как сейчас, один аккаунт из `.env`. |

Значения из `.env` имеют приоритет над одноимёнными переменными окружения оболочки.

## Как это работает

Каждое входящее сообщение записывается в SQLite вместе с медиа, потому что после
удаления ссылка на файл на серверах Telegram становится нерабочей. Событие удаления
несёт только id сообщений — а id чата есть лишь для каналов и супергрупп, — поэтому
без кеша осмысленный отчёт вообще невозможен.

Апдейт об удалении Telegram не гарантирует: он теряется на разрыве соединения, а
автоудаление по таймеру чата клиентам не всегда рассылается вовсе. Поэтому раз в
`RECONCILE_INTERVAL_MIN` минут бот спрашивает Telegram, живы ли ещё закешированные
сообщения за последние `RECONCILE_WINDOW_HOURS` часов, и присылает отчёт по тем,
которых там уже нет. За один проход уходит не больше 30 отчётов — остальное
переносится на следующий, чтобы не поймать FloodWait.

## Команды

Отправьте в `LOG_TARGET` (по умолчанию Избранное), от своего же аккаунта — команды
от чужих исходящих сообщений (`out=False`) игнорируются, это важно если `LOG_TARGET`
не `me`, а общий чат:

- `/watch @username` или `/watch -100123456` — начать следить за чатом. Также можно
  переслать любое сообщение из нужного чата в Избранное и ответить на него `/watch`
  без аргумента.
- `/unwatch @username` — то же самое, но снять с отслеживания. Если список опустеет,
  бот снова следит за всеми чатами (как при пустом `WATCH_CHATS`).
- `/list` — показать текущий список отслеживаемых чатов, с названием и `@username`,
  если известны. Длинный список разбивается на несколько сообщений, чтобы не упереться
  в лимит Telegram на длину сообщения.
- `/purge <дни>` — удалить сообщения за последние N дней из всех чатов (сначала
  показывает, сколько попадёт под удаление; добавь `confirm` в конец, чтобы
  реально удалить). `/purge @username` или `/purge -100123456` — то же для
  истории одного чата целиком; `/purge @username <дни>` — чат плюс последние N дней.
  Отрицательный id работает для групп/каналов; для личных чатов используй @username.
  Без аргументов — подсказка по синтаксису.
- `/help` — список всех команд с кратким синтаксисом.

Изменения применяются сразу, без перезапуска бота.

## Ограничения

- Удаление сообщения, которого нет в кеше (бот не видел его при отправке), отчётом
  не станет — сверять нечего. Такой промах пишется в лог с уровнем WARNING.
- Сверка догоняет пропущенные удаления не мгновенно, а на очередном проходе, и
  только внутри окна `RECONCILE_WINDOW_HOURS`.
- Backfill запускается только при непустом списке отслеживаемых чатов.
- `RETENTION_DAYS` удаляет и кешированные медиафайлы для вычищенных строк, а не
  только строки в базе.
- История редактирования сообщений пишется в базу (таблица `edits`), но пока не
  показывается в отчётах об удалении/редактировании — `format_deleted` выводит
  только последний текст. Это задел под будущую команду истории, а не баг.

## Безопасность

Файл `.session` даёт полный доступ к вашему аккаунту. Никогда не коммитьте и не
передавайте его. `.gitignore` уже покрывает `*.session`, `*.db*`, `.env` и `media/`.
